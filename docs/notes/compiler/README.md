# Compiler

How mansio turns a logical plan or a schema into SQL. The TypeScript compiler lives in `core/plan.ts` and
`core/compile/` (`dialect.ts`, `select.ts`, `ddl.ts`, `write.ts`, `decode.ts`). It is the oracle for the Go
port in `server/internal/doccompile` (ADR 0010): SQL text, bind values, check order and every error field must
match it exactly. Everything in `core/compile/` is pure: nothing throws, and failures come back as a
`CompileError`, `SchemaError` or `DecodeError` in an `Either`. Snapshot of real output:
`core/compile/GENERATED_SQL.txt`, regenerated by `deno task explain`.

- [How `compileSelect` turns a read plan into SQL](compile-select.md): check order, `hasOwn` table and field
  lookup, placeholder numbering, `expression` per layout and dialect, how each part of a plan changes the SQL,
  and every refusal.

## The DuckDB dialect

The compiler still has two dialects, `sqlite` and `duckdb`. No server path runs the DuckDB one: the Go server
executes SQLite only. The DuckDB dialect stays because `core/compile/GENERATED_SQL.txt` prints both and the Go
port (`server/internal/doccompile/dialect.go`) must stay byte-identical to it.

Dropping it would make the compiler about 20–30 lines smaller out of roughly 620 in `core/plan.ts` +
`core/compile/` (estimate from reading the code on 2026-11-05; nobody has made the change):

- `dialect.ts`: drop `Dialect` and `placeholder`; every placeholder is `?`.
- `expression`: drop the DuckDB branch (the `BIGINT`, `DOUBLE` and `BOOLEAN`→`INTEGER` casts around
  `json_extract_string`). SQLite keeps `json_extract`, with `CAST(… AS REAL)` for `number` fields.
- `compileSelect`: `bind` returns `?`; the target is always the quoted table name (no `"app".` prefix); it and
  `expression` lose their dialect argument.
- The dialect dimension in `tests/property/compiler_test.ts`, `compiler_arbitraries.ts` and
  `tests/unit/compile_test.ts`, and the DuckDB rows of `GENERATED_SQL.txt`.

`NULLS FIRST` / `NULLS LAST` are SQLite's defaults already (NULL sorts lowest), so they could go too; keeping
them costs nothing and keeps the intent explicit. The rest of the compiler (limit rule, schema validation,
identifier checks, null handling, ordering tie-breaker, count/countBy, `json` layout, decode) is SQLite work
and stays.
