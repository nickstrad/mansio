## How a mutation becomes one request

1. `client.mutation(name, args)` looks the handler up locally (`UnknownHandlerError` 404 /
   `HandlerKindMismatch` 400, as the server did) and runs `definition.invoke(recording, args)`.
2. `recording.get(t, id)`: first time, one query request `[get]`; the answer is the entry's **base** and the
   entry is **guarded**. Later gets answer from the cache, with the run's buffered writes applied (a patch
   bumps `_version` as the server will; an insert's `_creationTime` is the caller's clock — provisional).
3. `recording.find(...)` builds the same `SelectPlan` as `Documents`; with no buffered writes to that table it
   is one query `[select]`. With writes it sends **one** query (one snapshot)
   `[select with limit + displaced,
   get displaced…]`, where _displaced_ are the documents the run patched
   or deleted (an insert's fresh id has no server row, so it is not counted or fetched). A displaced document
   the run had not read takes that get as its base. `overlay` drops the touched documents' server state, adds
   their local state where it matches, and re-sorts/re-cuts (`count`/`countBy` adjusted the same way): exact,
   because at most `displaced` rows (groups) drop out. The widened limit is capped at 1000 (no cursor in v1):
   when the cap bites and the server's answer is full, the correction is accepted only if it still has `limit`
   entries none of which sorts after the server's last row; otherwise the handler fails `RuleError find-limit`
   (loud, never short). More than 63 displaced documents in one table fails `RuleError ir-op-limit`. Neither
   the find nor the documents it returns are asserted.
4. `insert` draws a UUIDv7 and answers it; `patch`/`delete` answer nothing; all are appended to the op list. A
   patch of a document the run knows is missing fails `NotFoundError` locally.
5. On return: `ops = [assert per guarded entry (version, or exists:false)] ++ writes`. Empty → no request (a
   handler that read nothing and wrote nothing). More than 64 ops fails locally (`RuleError ir-op-limit`,
   400). Otherwise one mutation with a fresh `requestId` per handler run (transport retries of that commit
   resend the same body and id).

**Derived vs app conflict.** Asserts are always the first `asserts` ops, so a `ConflictError` whose
`op <
asserts` is ours (re-run), and so is `check: "exists"` on an insert (a client-id collision: a re-run
draws new ids). Every other conflict goes to the caller. App conflicts never reach the server: `makeMove`
checks `expectedVersion` against what it read and fails locally. Re-runs: `handlerRetries` (4), pause
`random · min(250, 10·2^run)` ms, never past the call's deadline (`timeoutMs`, 10 s, covering all runs).

**Errors.** Read failures inside a handler escape as a private defect (`Escape`) so `DbError` stays the
handler's channel, and come out as the `ClientError` they were. Handler failures become `RemoteError` with
`toHttpStatus` of their tag and the error as `cause` (so e2e `remoteError(…, 409, "ConflictError")` holds on
every backend). `Unavailable` (new in `core/errors.ts`) is "no definite answer": `code`, `mayHaveApplied`.

## Transport

Same decisions as `internal/client/decide.go`: `shed`/`unavailable`/`aborted`/`expired` retry with
`max(Retry-After, full jitter 50 ms·2^n ≤ 5 s)`, 3 attempts, budget 0.1/first with burst 10;
`wrong_owner`/`fenced`/`ticket_invalid`/no answer reroute (≤ 5, no budget). The body is built once with
`canonical`, so a retried mutation keeps its `requestId` and a commit that landed answers `duplicate: true`.
`X-Timeout-Ms` = time left minus min(10 %, 100 ms). Static routes: a no-answer retries the same endpoint, a
`ticket_invalid` asks a token function again, `wrong_owner`/`fenced` are final (`Unavailable`). Locator
routes: `POST /v1/resolve {"tenant","app"[,"create"][,"min_epoch"]}`, cached until TTL − min(TTL/10, 1 s),
background refresh at 80 % ± 10 %, single-flight, `min_epoch = epoch + 1` after `wrong_owner`/`fenced`, the
primary's answer clears it. Only unit-tested against a fake controld (multi-node e2e is IR-5).

## The Deno shim

`POST /apps/:appId/v1/ops`, not `/v1/ops`: the app is in the path so auth runs **before the body is read**, as
on every other app route (a bare `/v1/ops` would have to read 64 KiB to learn which app's token to check).
Auth is `withAppAuthentication`: the app token with TENANCY=off, a tenant API key / session otherwise — so the
documents scenario's api-key half runs on the shim too. `db.app` must equal the path's app; `db.tenant` is
ignored (credentials decide, as the handler routes already ignore client tenant fields). Body: raw bytes under
the IR cap (65 536), `decodeBody` (strict JSON). Run: `Storage.ir` → writer queue (`QueueFullError` → 503
`shed`, `Retry-After: 1`), one `BEGIN IMMEDIATE` transaction (queries too: they share the writer queue, so
heavy writes can shed them, and do not use the reader process — the shim's limit until IR-6), `sql`/`tx`
events, the unbounded-select deadline. `_mansio_requests` is created by the first IR mutation, once per
Storage (so files that never saw one keep today's table list). `X-Timeout-Ms` (1..3 600 000; bad → 400 at
`header:X-Timeout-Ms`) bounds the run; past it `expired` 504, with `fields.ambiguous: true` for a mutation
(the deadline can land after COMMIT; the SDK retries with the same `requestId`). Every execute vector also
runs through `Storage.ir` (`ir_vectors_test.ts`).

## E2E on both backends

```sh
work-scripts/bash/e2e-linux.sh deno                       # all 7 scenarios on Deno
work-scripts/bash/e2e-linux.sh go                         # documents + queries on agentd; 5 skipped (IR-4)
work-scripts/bash/e2e-linux.sh deno --filter "/documents|queries/"
BACKEND=go deno task e2e                                  # on a Linux host with Docker and Go
```

The script exists because the suite needs Linux (`/proc`, `setsid`, the FFI binding) and Docker Compose cannot
publish Postgres to a container's loopback: it runs `postgres:17` on a private network (`E2E_POSTGRES_URL`,
which `main.ts` now accepts instead of starting Compose), cross-compiles agentd for Linux on the host
(`AGENTD_BIN`), and mounts the checkout and its git common dir at their host paths (the hermeticity check runs
`git status`). For Go, `startGoAgent` writes a fresh Ed25519 issuer (`keys.json`), an empty `local:<app>.db`
per app (static mode serves only files present at start), `schemas/<app>/v1.json` in each app's layout, and an
agentd config with `listen 127.0.0.1:0` + `-addr-file`; tickets are minted per request kind (read for queries,
write for mutations), 10 min TTL. Both layouts: the scenarios loop over `tic-tac-toe` (columns) and
`tic-tac-toe-json` (json). Results on this branch: Deno 7/7, Go 2/2 + 5 skipped.

The other five scenarios use `legacyClient` (server-side handlers) on Deno: they test tenancy, auth, backups
and the event log of that path, and log analysis reads `handler` events the SDK path does not emit.

## Traps

- **Schema layout is part of the fingerprint.** A client for `tic-tac-toe-json` must pass
  `withStorage(schema, "json")`, else every request is `SchemaDriftError`.
- **`createClient` throws** without `endpoint`, `locator` or `transport` (programming error at startup).
- **DST-1 with the SDK client** is not done: DST-1 (`dst/1-single-node`) has not landed. Plug-in point: the
  SDK's seams (`transport`, `fetch`, `now`, `random`, `sleep`, `newId`, `newRequestId`) drive it
  deterministically; the Go sim needs either a Go client that sends what the SDK sends (asserts first, same
  body on transport retry, new id on re-run — pinned by the `sdk:` vectors) or a fetch bridge into the sim's
  HTTP handler.
- `find` inside a mutation is unguarded (v1): neither the answer nor the documents it returns are asserted, so
  a decision on what a `find` saw ("no row matches", "this row's version") is not protected; `get` what a
  decision depends on. Two reads in a query handler are two snapshots.
