# 2026-11-05 — fetch bulkhead (RI-02) on SeaweedFS

By the p3-vactor agent (Release It plan RI-02). Short runs, same rig as `2026-11-04-sizes/`, SeaweedFS at
`localhost:8333` possibly shared with other agents' gated tests. Plain mode (coldload's `s3Fetcher`), so the
bulkhead bounds fetches by **count only**: a plain `Fetcher` does not know the size before it fetches.

| class | bulkhead | c=16 | c=64 |
|---|---|---|---|
| 16 MiB (n=64) | default 16 | 14.3 act/s (295 MB/s) | 14.4 act/s (296 MB/s) |
| 128 MiB (n=16) | default 16 | **all 16 failed** | **all 16 failed** |
| 128 MiB (n=16) | `max_fetches: 4` | 1.9 act/s (267 MB/s) | 1.8 act/s (254 MB/s) |

Before the bulkhead (2026-11-04): 132 MiB at c=16 gave 163 MB/s and c=64 134 MB/s.

Finding: with 16 large fetches in flight, every 128 MiB GET hit objstore's own transfer deadline
(`OpTimeout + size/MinThroughput` = 5 s + 4.1 s, RI-01): 16 × 128 MiB share ~260 MB/s, so each transfer
gets ~16 MB/s, below the 32 MiB/s floor. objstore retried each GET (idempotent) and failed again
(`S3.REQUEST_RETRIED`, kind transient). The per-transfer throughput floor and the bulkhead must agree:
in-flight bytes ≤ aggregate bandwidth × (OpTimeout + size/MinThroughput). Durable mode's byte cap (1 GiB:
8 × 128 MiB, ~4.3 s on this rig) stays inside it; plain mode needs a smaller `max_fetches` for large files,
or a Fetcher that reports the size first.

Config: `max_fetches`, `max_fetch_queue`, `activation_timeout` (default 10 m in coldload) in
`configs/coldload/*.json`.
