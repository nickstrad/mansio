The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. Where this text and the reference
implementation disagree, the vectors decide; a disagreement the vectors do not cover is a bug in this text and
gets a vector when it is fixed.

## 1. Model

A **database** is named by `(tenant, app)` and holds the tables of one registered schema. A **request** is
either a **query** (1–64 read operations) or a **mutation** (1–64 operations, applied atomically, in order).
The response is one result per operation, or one error.

Paths in this document and in error `fields.path` use `core/schema.ts`'s style: `a.b` for a member, `a[3]` for
an element. Envelope paths are absolute (`ops[2].expect.version`); a document-value path is the field path
inside the body (`grid[1]`), with the operation identified by the error's `op`.

## 2. Schema and fingerprint

A schema is registered as the JSON form of a `defineSchema` value, which is exactly `JSON.stringify(schema)`:

```text
{
  "<table>": {
    "fields": { "<field>": { "node": <Node> } },
    "storage": "columns" | "json",
    "indexes": [{ "name": "<name>", "fields": ["<field>", ...] }]
  }
}
```

`Node` is
`{ "kind": "string" | "number" | "integer" | "boolean" | "enum" | "array", "nullable"?: bool,
"values"?: [string...], "item"?: Node, "length"?: int }`.
`values` is required on (and only allowed on) an `enum` and its members are distinct; `item` is required on
(and only allowed on) an `array`; `length` is only allowed on an `array` and is a non-negative safe integer.
Unknown members are rejected.

The declaration rules of `core/schema.ts` apply (vectors: `schema.json`): table and field names match
`^[A-Za-z_][A-Za-z0-9_]*$` (`invalid-identifier`); fields starting with `_` are reserved (`reserved-field`);
tables starting with `_` or, in any case, `sqlite_` are reserved (`reserved-table`); no enum member contains
U+0000; an index names one or more declared non-array fields (`empty-index`, `unindexable-field`) and its name
is unique in the table (`duplicate-index`); an enum with zero values fails DDL (`CompileError empty-enum`).

The **fingerprint text** is the schema JSON re-serialized with members in the order received and no whitespace
(`JSON.stringify` of the decoded schema). It is what `_platform_schema.definition` stores, byte for byte, so
existing database files open unchanged. The **fingerprint** is `sha256:` followed by the 64 lowercase hex
digits of SHA-256 over the UTF-8 bytes of the fingerprint text. The storage layout is part of the text: the
same tables under `columns` and `json` have different fingerprints.

## 3. Transport and body

`POST /v1/ops`, headers `Authorization: Bearer <ticket | api key | session>`,
`Content-Type:
application/json`, optional `X-Trace-Id` and `X-Timeout-Ms`. Authentication, routing and
deadlines are the server's concern and are not part of the vectors.

The body is decoded in this order; the first failure is the answer:

1. **Size.** More than 65 536 bytes is `RequestTooLarge` (413, `fields.limit = 65536`). Exactly 65 536 is
   accepted.
2. **UTF-8.** Bytes that are not well-formed UTF-8 are `SchemaError` (`type-mismatch`, path `body`). A
   byte-order mark is not stripped (and so is not JSON).
3. **Strict JSON** (RFC 8259) with four refusals beyond the grammar, each a `SchemaError` `type-mismatch`:
   - a **duplicate member name** in any object (path: the duplicate member, e.g. `ops[0].table`);
   - a number whose value is not a finite IEEE-754 double (`1e400`; path: the member);
   - a string that, after escapes, holds a **lone surrogate** (`"\ud800"`; path: the member);
   - nesting deeper than 64 arrays/objects: the top-level value is at depth 0, and a container opened inside
     64 others is refused at its own path; scalars never count. A lone surrogate in a member _name_ is
     reported at that member's path.

   Malformed text, trailing text and other grammar errors report path `body` (or the innermost container where
   the parser stopped). A number literal denotes its double value: `10.0` is `10`, and `9007199254740993` is
   `9007199254740992`.
4. **Envelope** (§4), then **operations** (§5), checked in the order those sections list. The vectors contain
   one defect per request; for a request with several defects only the reported tag is normative, not which
   defect is reported.

Every decode failure is a `SchemaError` with `reason` `unknown-field` (a member v1 does not define),
`not-an-object` (an object was required) or `type-mismatch` (everything else), except the size cap. When the
path is inside `ops[i]`, the error carries `op: i`.

## 4. Envelope

```json
{ "v": 1, "db": { "tenant": "acme", "app": "notes" }, "kind": "mutation",
  "requestId": "01JD…", "schema": "sha256:…", "ops": [ … ] }
```

| Member      | Rule                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------ |
| (body)      | an object with only the members below                                                                                    |
| `v`         | the number `1`                                                                                                           |
| `db`        | `{tenant, app}`, nothing else; each a **wire id**: 1–64 bytes of `[A-Za-z0-9._:-]`, not starting with `.`                |
| `kind`      | `"query"` or `"mutation"`                                                                                                |
| `requestId` | a wire id; **required** for a mutation; optional for a query, where it is ignored                                        |
| `schema`    | `sha256:` + 64 lowercase hex digits: the fingerprint the client compiled against                                         |
| `ops`       | an array of 1–64 operations; in a query, every operation is `select` or `get` (otherwise `type-mismatch` at `ops[i].op`) |

The wire-id rule is mansio-server's `front.checkID`, so ids can name files and log lines safely.

## 5. Operations

Every operation is an object with `op` first checked against the closed vocabulary, then the members of that
op only. `table` is a string in every op; whether it names a table is an execution check
(`CompileError
unknown-collection`).

| `op`     | Members (required **bold**)                                   | Result                                                                |
| -------- | ------------------------------------------------------------- | --------------------------------------------------------------------- |
| `select` | **`table`**, **`filters`**, **`limit`**, `order`, `aggregate` | documents `[doc…]`; `count`: a number; `countBy`: `[{value, count}…]` |
| `get`    | **`table`**, **`id`**                                         | the document, or `null`                                               |
| `insert` | **`table`**, **`value`**, `id`                                | the new `_id` (a string)                                              |
| `patch`  | **`table`**, **`id`**, **`value`**, `expect`                  | `{"_version": n}`, the new version                                    |
| `delete` | **`table`**, **`id`**, `expect`                               | `{"deleted": true \| false}`                                          |
| `assert` | **`table`**, **`id`**, **`expect`**                           | `null`                                                                |

A **document** is the body's declared fields plus `_id` (string), `_creationTime` (integer ms) and `_version`
(integer ≥ 1). Member order in results is not significant.

### 5.1 `select`

The `SelectPlan` of `core/plan.ts` without `kind`:

- `filters`: an array (possibly empty) of `{field, op, value}`, all three required; `field` a string, `op`
  `"eq"` or `"gt"`, `value` any JSON value or a `$ref` (§5.3). Filters are ANDed.
- `limit`: a JSON number. Its range (an integer in 1..1000) is checked at execution:
  `CompileError
  invalid-limit`.
- `order`: `{field, direction}`, `direction` `"asc"` or `"desc"`.
- `aggregate`: `{"kind": "count"}` (no other member) or `{"kind": "countBy", "field": <string>}`.

Semantics are today's compiler's (`core/compile/select.ts`; vectors: `compile.json`, `execute.json`):

- `eq null` matches SQL NULL. `gt` requires a numeric field and a non-null value (`gt-requires-numeric`).
- Filter and order fields are declared fields or `_id`, `_creationTime`, `_version`; unknown names are
  `unknown-field`; array fields are `array-predicate`. Filter values are validated against the field's node
  (`SchemaError`, path = field) and must not contain U+0000.
- **Ordering:** without `order`, `_id ASC`. With `order`, the field in the given direction, NULLs first when
  ascending and last when descending, then always `_id ASC` as the tie-break, so equal keys come back in a
  deterministic order.
- `count` counts every matching row and ignores `limit` and `order`. `countBy` groups by the field's value,
  orders groups by value ascending with NULL first, ignores `order`, and `limit` caps the number of groups.

### 5.2 `get`, `insert`, `patch`, `delete`, `assert`

- **Id positions** (`get`, `patch`, `delete`, `assert` `id`): a non-empty string without U+0000, or a `$ref`.
  Any string is an id; server-issued ids need not be UUIDs. Any other value, including an object or array
  without `$ref`, is `type-mismatch` at the id's path.
- **`insert.value`** and **`patch.value`**: objects. Their contents are validated at execution: an insert body
  with `core/schema.ts`'s `parseObject` (every declared field present, no unknown or `_`-prefixed member), a
  patch body with `partial = true` (absent members untouched; `{}` is a valid patch). Then the text storage
  contract: no string anywhere in the body holds U+0000 (`SchemaError type-mismatch`, `expected` "text without
  U+0000", path = the field, e.g. `tags[1]`). Values may contain `$ref`s.
- **`insert.id`**: a client-generated id, a canonical lowercase UUIDv7 —
  `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Not a `$ref`. An insert carries an
  implicit `expect: {"exists": false}` on that id: if a document with the id exists in the table at that point
  of the request, the answer is `ConflictError` with `check: "exists"`, `expected: false`, `actual:
  true`.
  Without `id` the server draws one (§6.3).
- **`patch`** of a missing document is `NotFoundError` (404, `fields {table, id}`), after `expect` is checked.
- **`delete`** of a missing document is not an error: it answers `{"deleted": false}` unless `expect` requires
  existence.
- **`assert`** writes nothing and answers `null`.
- An `insert` has no `expect` member.

### 5.3 References: `$ref`

`{"$ref": i}` stands for the `_id` that operation `i` of the same request produced. Decode requires `i` to be
an integer with `0 <= i < current index` and operation `i` to be an `insert`; anything else is
`SchemaError
type-mismatch` at `….$ref`. A reference object has exactly the one member (`unknown-field`
otherwise).

References may appear in every id position (except `insert.id`), and anywhere inside an insert or patch
`value`, a filter `value` and an `expect.fields` value, including inside arrays. Because no document value is
an object, any object with a `$ref` member at a value position is a reference; other objects are left to
validation, which rejects them. A query has no inserts, so it can contain no valid reference. References are
resolved before the operation is validated, so `{"listId": {"$ref": 0}}` validates as a string.

### 5.4 Preconditions: `expect`

`expect` is an object with at least one of:

- `version`: a safe integer ≥ 1 — the document's `_version` must equal it;
- `exists`: a boolean — the document must (not) exist;
- `fields`: a non-empty object `{field: value}` — each named field must equal the value.

`version` and `fields` imply `exists: true`. `exists: false` together with `version` or `fields` is a decode
error (at `expect.exists`), and so is `exists: false` on a `patch` (it could never succeed). Unknown members
are rejected (`range` is reserved for v1.1).

At execution, `expect.fields` names declared, non-array fields only (`CompileError unknown-field` — which
includes `_id`, `_version` and `_creationTime`; use `version` — or `array-predicate`); each value is validated
against its node and the storage contract. This happens whether or not the document exists. Then the checks
run in this order, and the first that fails answers `ConflictError` (409):

| `check`   | Fails when                                                  | `expected`              | `actual`                                     |
| --------- | ----------------------------------------------------------- | ----------------------- | -------------------------------------------- |
| `exists`  | existence (explicit or implied) differs                     | `true` / `false`        | `false` / `true`                             |
| `version` | `_version` differs                                          | the expected version    | the stored `_version`                        |
| `fields`  | any named field differs (strict equality of the JSON value) | the `expect.fields` map | the stored values of those fields, same keys |

The error's `fields` also carry `table` and `id` (the resolved id). Equality is on decoded values: `null`
equals only `null`, numbers compare as doubles, booleans as booleans.

## 6. Execution

### 6.1 Order of checks for one request

1. Decode (§3–§5).
2. Routing and authorization (server; not vectored).
3. **Fingerprint:** `schema` must equal the database's fingerprint, else `SchemaDriftError` (409, no `op`,
   `fields {expected, actual}` with `actual` the request's value). Nothing runs.
4. **Duplicate check** (mutations only, §7).
5. Operations, in order. For each, the table lookup comes first (`CompileError unknown-collection`), then:
   - `select`/`get`: compile (limit, fields, values) and read;
   - `insert`: body validation, then the client-id existence check, then the write;
   - `patch`: body validation, then load, then `expect`, then `NotFoundError` if missing, then the write;
   - `delete`/`assert`: load, then `expect`, then the delete (if present) / nothing.

### 6.2 Atomicity and visibility

A request runs in one transaction (the reference executor: `BEGIN IMMEDIATE` … `COMMIT` for a mutation,
`BEGIN` … `COMMIT` for a query; mansio-server: one savepoint inside the actor's group-commit batch). Any
failure rolls back every operation of the request and its request-id record: a failed mutation leaves no
trace. Operations see the writes of earlier operations of the same request (a `select` after an `insert`
counts it; a `delete` frees an id for a later `insert`). A failing operation's index is the error's `op`.

A query sees one consistent snapshot of committed state and never writes.

### 6.3 Server-owned fields and determinism

- `_creationTime`: the server reads its clock **once per request**; every insert of the request gets that
  value. A patch never changes `_creationTime`.
- `_version`: `1` on insert; each patch sets `_version = _version + 1` in SQL (also for `{}`), and reports the
  new value.
- `_id`: the client's `insert.id`, or one drawn from the server's id generator, once per insert without `id`,
  in operation order. Server ids are opaque, unique strings (mansio-server: UUIDv7; the Deno backend today:
  UUIDv4).

Given the database state, the request, the clock reading and the id sequence, the result and the final state
are fully determined: there is no other randomness or time. Execute vectors fix the clock and the id sequence
per step.

### 6.4 Writes

Writes go through `core/compile/write.ts`: an insert binds every column (booleans as 0/1, arrays as JSON text;
the `json` layout stores the body as one JSON `doc`); a patch is read, merge (`{...stored, ...patch}`) and a
full replace; a delete is by `_id`. Values are only ever bind parameters.

## 7. Request ids and duplicates

The semantics are mansio-server's (`internal/actor/reqid.go`, `knowledge/front/2026-11-05-request-ids.md` in
mansio-server):

- Scope: one database. The same `requestId` on two databases is two requests.
- Mutations only. A query's `requestId` is ignored: queries are never deduplicated.
- Only applied mutations are remembered. The record is written inside the mutation's transaction, so a
  mutation that fails leaves its id unused and a retry with the same id runs again.
- A mutation whose `requestId` this database already applied is answered **200 with the original `result` and
  `"duplicate": true`**, and nothing runs — the new operations are decoded but not validated or executed. The
  payload is not compared: the same id with a different payload gets the first answer. Clients MUST NOT reuse
  ids.
- The fingerprint check (§6.1 step 3) still runs first.
- Storage: mansio-server's table, byte for byte:
  `_mansio_requests(request_id text not null primary key, applied_ms integer not null, result blob) strict,
  without rowid`,
  plus the `applied_ms` index. `applied_ms` is the request's clock reading. `result` is the version byte
  `0x02` followed by the UTF-8 canonical JSON (§9) of the `result` array (version `0x01` is mansio-server's
  raw-SQL outcome encoding). Retention: mansio-server's `RequestTTL` (default 24 h); a retry after it applies
  again.

## 8. Responses and errors

Success: `200 {"result": [<one per op>]}`, plus `"duplicate": true` on an already-applied mutation (the member
is absent otherwise).

Failure: the status below and

```json
{ "error": { "tag": "<tag>", "message": "<human text>", "op": <index>?, "fields": { … }? } }
```

- `tag` is normative and closed; clients switch on it.
- `op` is present exactly when the failure belongs to one operation (decode errors inside `ops[i]`, every
  execution error of operation `i`); absent for envelope failures, `SchemaDriftError` and transaction-level
  failures.
- `fields` is the failure's structured payload, present on 4xx only. 5xx bodies carry no `fields` and their
  `message` names only the tag (detail goes to the server log, as `platform/http/router.ts` does today).
- `message` is not normative.

| Tag                      | Status | `fields` (normative members)                 | When                                                                                                   |
| ------------------------ | ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `SchemaError`            | 400    | `reason`, `path`; also `expected`, `actual`  | decode failure (§3–§5); body, filter or `expect` value invalid (§5)                                    |
| `CompileError`           | 400    | `reason`; also `table`, `field`, `detail`    | unknown table/field, array predicate, `gt` misuse, invalid limit                                       |
| `NotFoundError`          | 404    | `table`, `id`                                | `patch` of a missing document                                                                          |
| `ConflictError`          | 409    | `table`, `id`, `check`, `expected`, `actual` | an `expect` failed; an insert's client id is taken                                                     |
| `SchemaDriftError`       | 409    | `expected` (database), `actual` (request)    | fingerprint mismatch                                                                                   |
| `RequestTooLarge`        | 413    | `limit`; also `observed`                     | body over 64 KiB                                                                                       |
| `DecodeError`            | 500    | —                                            | a stored row cannot be decoded (a server-side fault)                                                   |
| `StorageError`           | 500    | —                                            | a statement or transaction failed                                                                      |
| `Defect`                 | 500    | —                                            | a bug                                                                                                  |
| `StatementDeadlineError` | 504    | —                                            | a statement ran past the server's statement deadline; nothing changed                                  |
| `AuthError`              | 401    | `reason`                                     | missing or wrong credentials (Deno backend)                                                            |
| `ticket_invalid`         | 401    | —                                            | missing, expired or wrong ticket (mansio-server): get a new one                                        |
| `wrong_owner`            | 421    | —                                            | this node does not own the database: re-resolve                                                        |
| `fenced`                 | 421    | —                                            | the database is moving or suspended: re-resolve after `Retry-After`                                    |
| `aborted`                | 409    | —                                            | rolled back because another write in its batch failed: retry at once                                   |
| `shed`                   | 503    | —                                            | not accepted (load); nothing ran: retry after `Retry-After`                                            |
| `unavailable`            | 503    | —                                            | a dependency is down; nothing ran: retry after `Retry-After`                                           |
| `expired`                | 504    | `ambiguous`?                                 | deadline passed; with `ambiguous: true` a mutation may have committed: retry with the same `requestId` |

The first ten are produced by the protocol itself. The vectors cover `SchemaError`, `CompileError`,
`NotFoundError`, `ConflictError`, `SchemaDriftError` and `RequestTooLarge`; `DecodeError`, `StorageError`,
`Defect` and `StatementDeadlineError` are server faults with no request-only trigger, so no vector produces
them. The lowercase tags are mansio-server's wire codes (`internal/front/codes.go`) with their statuses,
passed through unchanged; a statement timeout on `/v1/ops` is reported as `StatementDeadlineError` (504), not
as mansio-server's raw-SQL `stmt_timeout` (422). Clients retry `shed`, `unavailable`, `aborted`, `expired` and
`wrong_owner`/`fenced` (after re-resolving) with the same `requestId`; a 4xx with a mansio tag fails the same
way on retry. `ConflictError` from a derived precondition makes the SDK re-run the handler (plan §3).

`reason` vocabularies are `core/errors.ts`'s `SchemaFailure` and `CompileFailure`.

## 9. Canonical encoding

The canonical JSON of a value is RFC 8785 (JCS): no insignificant whitespace; object members sorted by the
UTF-16 code units of their names; strings and numbers serialized exactly as ECMAScript `JSON.stringify` does
(shortest round-trip number form, `1e+21`, `-0` as `0`); absent (undefined) members omitted. It is used for
the stored duplicate result (§7) and for comparing requests (the SDK's "same op list" retry rule). Vectors:
accepted `decode.json` entries carry the canonical encoding of the decoded request.

## 10. Reserved for later versions

- Range preconditions (`expect.range` / `assert` over a select's ids or count), v1.1.
- Pagination cursors, schema migrations, server-enforced rules for untrusted callers.
- Any new op, member or tag requires `v: 2` or an additive minor revision of this document plus vectors; v1
  servers reject unknown members.

## 11. Decisions this spec makes beyond the plan

Recorded here so implementations do not have to rediscover them (plan §2 left them open):

1. `assert` answers `null`; `delete` answers `{"deleted": bool}`; `patch` answers the new `{"_version"}`;
   `insert` answers the bare id string.
2. An insert whose client id exists is `ConflictError` `check: "exists"` (an implicit
   `expect.exists:
   false`), not `StorageError`.
3. `version`/`fields` imply `exists: true`; on a missing document they fail as `check: "exists"`.
   `exists:
   false` cannot combine with them, and is refused on `patch`.
4. A patch checks `expect` before reporting `NotFoundError`; without `expect`, a missing document is
   `NotFoundError`.
5. `expect.fields` refuses metadata and array fields and validates values even when the document is missing.
6. A `$ref` must target an earlier `insert`; anything else is a decode error. References are allowed in id
   positions and inside values. An object or array without `$ref` in an id position is `type-mismatch`.
7. A query may hold 1–64 reads (not only one select), in one snapshot; a write in a query is a decode error
   (`SchemaError` at `ops[i].op`, 400), not `QueryWriteAttemptError` (500, which stays a server invariant).
8. `_creationTime` is one clock reading per request, shared by all its inserts and the request-id record.
9. Duplicate detection runs after the fingerprint check and before any validation of the operations.
10. The decoder refuses duplicate members, non-finite numbers, lone surrogates, invalid UTF-8 and a BOM, so TS
    and Go read the same bytes the same way.
11. The `limit` range, table names, field names and values are execution checks with today's tags; decode
    checks only shapes and closed vocabularies.
12. Server-side statement timeouts on `/v1/ops` are `StatementDeadlineError` (504).
